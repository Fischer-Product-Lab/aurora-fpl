# Aurora Run Explorer

Aurora Run Explorer is the portfolio-facing companion to the deterministic
agent orchestration lab. It loads portable JSON artifacts generated by the
Python simulator and turns them into guided, inspectable stories.

## Run locally

From the repository root, regenerate the data bundle:

```powershell
py -3 -m aurora_lab showcase --output dashboard/public/data
```

Then start the dashboard:

```powershell
cd dashboard
npm ci
npm run dev
```

Open `http://localhost:3000` for the cinematic title page. The Run Explorer
lives at `http://localhost:3000/demo`.

## What to demonstrate

- Choose **Watch replay** to present a recorded run as it unfolds. At 4× speed,
  a typical 66–68 second simulation takes about 17 seconds.
- Point out the live specialist states, plain-English "what happened / why it
  matters" explanation, audit updates, and deliberately hidden ending.
- Pause, scrub, change speed, or restart; switch to **Explore instantly** when
  you want the complete result without waiting.
- Start with the clean orchestration story for the architecture tour.
- Compare the planning fault with and without an independent critic.
- Compare permanent worker failure with and without bounded reassignment.
- Use the budget story to show atomic fallback admission, exact-fit control,
  safe refusal under tight capacity, and zero overspend.
- Open Timeline, Evidence, Governance, Verification, Budget, and Raw trace to
  move from the outcome to its underlying proof.

Story and run selections are encoded in `/demo?story=` and `/demo?run=`
parameters, so a specific comparison can be shared directly. Existing root
deep links with those query parameters redirect to `/demo`.

## Verification

```powershell
npm run lint
npx tsc --noEmit
npm test
```

The rendered tests validate the server shell and every manifest reference. Pure
replay tests verify tied-event ordering, progressive task and evidence state,
clock speed, outcome gating, and plain-English fallbacks. The dashboard
intentionally treats event kinds as open strings so future simulator events
remain visible through the generic trace renderer.

## Data contract

`public/data/manifest.json` is schema-versioned and references relative run and
report envelopes. Full run envelopes include the simulation result plus metrics
reconstructed from the trace; compact reports are never used as timeline data.

The dashboard is a static reader: its "live" view replays immutable recorded
events. It does not mutate simulation state or call a model at runtime.

## Deployment targets

The dashboard keeps two build targets from the same source:

- `npm run build` produces the existing Vinext/Cloudflare Sites bundle.
- `npm run build:vercel` produces the standard Next.js bundle used by Vercel.

For a Vercel Git import, select this repository and set the project root to
`dashboard`. The committed `vercel.json` selects the Next.js framework and the
Vercel build command. No environment variables are required for the recorded
simulation explorer.

## Security checks

Run `npm run security:public` before publishing. The check scans text-based
files under `public/` for credential patterns, personal contact details, local
machine paths, and IP addresses without printing any detected value. Keep model
recordings and real incident data outside `public/`; everything in that folder
must be treated as openly downloadable.

## Matched experiment workbench

The explorer opens on the selected experiment, with the plain-English guide and
portfolio case study available as expandable sections. Every displayed run is a
recorded synthetic simulation; selecting a run does not call a model or start a
new simulation.

Matched comparisons use only explicit `matched_control_for` relationships in the
manifest and require matching seed, incident variant, study, and strategy. They
show control and intervention metrics side by side. A missing recovery time is
not treated as zero. The first observable trace change compares event time, kind,
actor, task, and message in recorded order; it excludes metadata and does not
claim to establish causality. Select either event to inspect its full audit entry.
Budget comparisons distinguish the shared worker failure from the capacity
intervention, including the unchanged negative control.

During replay, comparison outcomes and detailed evidence remain hidden until the
recorded completion event or until **Explore instantly** is selected. The new
comparison contract is covered by `tests/comparison.test.mjs`. The Node runner
uses default test isolation, matching the compatibility fix proposed in PR #11.

### Production image policy

Aurora's UI uses committed static images and does not need on-demand image
transformation. The Worker rejects `/_vinext/image`, and Next sets
`images.unoptimized: true` for its local handler. Vercel's separate platform
pipeline can run before application routing. The explicit `images` configuration
in `vercel.json` sets empty local, remote and legacy-domain allowlists to deny
every optimizer source. Direct public
images, fonts, audio, and data remain accessible.

`npm run verify:vercel` builds Next and runs a loopback-only production HTTP test.
It confirms the local Next optimizer returns 404 and the Vercel optimizer
allowlists are empty, compares public asset bytes with the
committed files, checks the landing and demo routes, and verifies a run deep link.
Release checks must also verify that Vercel rejects ordinary local image
optimization requests (400 or 404) while serving the direct originals.
If adding optimized images later, revisit the policy explicitly and audit the
image-processing dependencies before enabling the endpoint.
